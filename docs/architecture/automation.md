# Service events, routines, connectors, scheduler and attendance

Part of the architecture notes for Claude Code; the index is in [CLAUDE.md](../../CLAUDE.md).

## Service storage and events (LIB-60..62, MET-1..2)

- **Core** `metrics/` (export `./metrics`): `SERVICE_STORAGE` (none, box, server), `EVENT_KINDS`, `serviceEventSchema` (strict: facts only), `newEvent`, `EventStore` (memory; D1 `createD1EventStore`, migration 0012 `service_events`), `serviceMetrics(events, journeys)` (starts, finishes, completion, hand-overs, open/closed/declined requests, weeks, and per journey a funnel, median time, waits per role, reassignments, failures, forms filled from words) and `activityLog`. Library entries carry `storage` (migration 0012), set by `setEntryStorage` (administrators); `published()` gives each service's `state` and `storage`.
- **Outcomes** (OUT-1..3): `result.outcome` (yaxb-journeys `OUTCOME_ID`, kept by `ServiceDesign`'s `resultOutcome`) comes back in `RunState.result.outcome`; `JourneyPanel` records `journey.outcome` (event field `outcome`); `serviceMetrics` gives `outcomes` per journey and service (labels from `journeys[].outcomes`).
- **Box**: `/v1/events` (POST a batch, GET `?service=&since=`).
- **Worker**: `PUT /api/library/entries/:id/storage` (server needs `CASES_CENTRAL`, the paid plan), `POST /api/events` (only for services stored on the server), `GET /api/events?service=` (administrators, moderators, reviewers).
- **Web**: `composables/service-events.ts` (`recordEvent`, batched, kept offline) fed by `JourneyPanel` (started, screen reached, finished, handed, stopped, step failed, form filled from words, a member's answer) and request actions (`CaseView`: picked up, closed, declined; `RequestBoard`: reassigned). `AddServiceFlow.vue` (Add, People, Storage) in My notebook → Services, and "People and storage" on a loaded service.

## Routines and hooks (RTN-1..9, 11..13)

- Core `routines/` (export `./routines`): `kind: routine` (`on`: `schedule` { every hour/day/week/month, at, minute, on } | `event` { service, kind, journey?, outcome? } | `date` { service, date, before, at }; `when`; `actions`: message { to, text }, summary { service, days, as }, connector { call, with, as }, record { outcome }; `utc_offset`, India by default), `parseRoutine`, `nextScheduled`/`isDue` (more than `MAX_LATE_MS` late is skipped), `matchesEvent`, `runRoutine` (limits, pause, `looksLikePayment` refuses, `dryRunHandlers`, `preview`), `runEvents`/`runsFromEvents` (routine.* events, facts only), `RoutineStore` (notices, settings, usage; memory and `createD1RoutineStore`, migration 0019, which also adds `service_events.outcome`), `ROUTINE_STARTERS`. Library: entry kind `routine`, written by `ROUTINE_AUTHORS` (administrator, the new `automator` role; `writesRoutines`), approved by a reviewer; `publishedRoutines`; `published().routines` (event triggers only).
- Worker `worker/routines.ts`: `runOnce` claims a run id in `service_events` (`rs-<id>`) before running, so a retried event or an overlapping sweep never runs twice; `fireEvents` (from POST /api/events, and `/api/routines/events`, which kiosks use for services keeping events elsewhere: not stored, only the runs), `sweepTenant`/`sweep` (the `scheduled()` Cron Trigger, `*/15 * * * *` in wrangler.jsonc, every edition and tenant with a published routine). A message is a notice for the role (My work); a summary reads the service's server events (`storage: server` only); a connector call unseals its secrets. Routes `/api/routines` (overview, starters), `/:entry/runs`, `/dry-run`, `/:entry/run` (administrators, audited), `/settings` (PUT, administrators, audited), `/notices[/:id/done]`, `/events`. Tests: `worker/test/routines.test.ts`.
- Web: the catalogue's Routines screen (`catalogue/RoutinesScreen.vue`: published routines in words (`lib/routines.ts` `triggerText`), Run now, starters via `?service=new&routine=<id>|blank`, limits and pause), `ServiceWorkspace` views YAML, Dry run (`RoutineDryRun.vue`), Runs (`RoutineRuns.vue`), Audit, History; notices in `MyWork.vue`; `service-events.ts` forwards events a published routine waits for (`publishedRoutineTriggers`). Not built: journey and agent actions, incoming webhook triggers, the box running routines offline.
- Approvals (RTN-6): `approve: <role>` on a message, connector or webhook action; `runRoutine` hands it to `handlers.approval` as a `PendingAction` (rendered then), the store keeps `RoutineApproval`s (migration 0020), `sendPending` sends an approved one under the same rules; Worker `decideApproval` (the first decision counts; logged as a `routine.action` of the same run), `/api/routines/approvals[/:id]` (audited), `components/routines/RoutineInbox.vue` (approvals and notices) in My work.
- Webhooks (RTN-8): action `webhook { url (https), with }`, body `webhookBody` (routine, run, trigger, the event's facts, `data`), `sendWebhook` (SSRF guard, no redirects, 10 s) signed with `webhookKey(SESSION_SECRET, "<edition>|<tenant>|<entry>")` (`X-Anjal-Timestamp`, `X-Anjal-Signature: sha256=` HMAC of `<timestamp>.<body>`); `GET /api/routines/:entry/signing-key` (administrators, audited), shown in the Runs view.
- Guard hooks (RTN-9, 11): yaxb-journeys `Step.guard` (`{ allow, reason }` or `{ call, with, within, reason }`, `guardProblems`; nested screens and `StepForm.guardYaml` carry it), the runner's `guard` state between asking and run (`guardVerdict`: only `allow: true`, a connector's `{ ok, data: { allow, reason } }`; late or failing is a no), `RunState.refused` shown by JourneyPanel and JourneyRunner; the answer is kept in `steps["guard:<step>"]` (`guardKey`) and `replay` reads it back (a refused replay is invalid). Guard calls count as services in journey summaries.
- Family (RTN-12): `FAMILY_ROUTINES` (notes to the parents, `to: administrator`), library `switchRoutine` (administrators; published at once, or archived), `/api/routines/family[/:id]`, `settings/FamilyRoutines.vue` (Preferences → Family routines, where `household` is offered); in Family `FAMILY_APPROVER` makes connector calls and webhooks wait for a parent.

## Connectors (CNX-1..3, 5..8)

- Core `connectors/` (export `./connectors`): `parseConnector`/`compileConnector`, `connectorHandlers`, `parseConnectorHandler`, `connectorSecrets` (names), `buildConnectorRequest` (input into `{{input.x}}`, URL-encoded in the path; the secret added last), `callConnector` (SSRF guard, no redirects, 10 s, 200 KB, `untrusted`), `ConnectorSecretStore` (memory; D1 `createD1ConnectorSecretStore`, migration 0018 `connector_secrets`). Library: entry kind `connector` (administrators), `publishedConnectors`, connectors' handlers in `compileOptions`, `published().connectors` (names of secrets only). `serviceInfo` (journeys/summary.ts) marks `connector.*` as `outside` for summaries and the guardian.
- Worker: `POST /api/connectors/:id/:op` (same origin, chat limiter, only an operation a published journey uses; secrets unsealed with SESSION_SECRET), `GET|PUT|DELETE /api/library/connectors/:id/secrets[/:name]` (administrators). Web: KioskShell's `services` is a Proxy that sends any `connector.*` step there (`connectorCall`); `journeyServiceNames` (library.ts); ServiceWorkspace shows YAML, Secrets (`catalogue/ConnectorSecrets.vue`), Audit and History for a connector.
- A business's own MCP server (CNX-1): a connector with `mcp: { url, tools }` (no base or operations; auth none, bearer or header), `mcpServerOfConnector` (id `org-<id>`, the secret in the header), `guardedFetch` (SSRF guard on every request, no redirects). The Worker's `orgMcpServers(env)` (kiosk.ts) feeds `createKiosk`'s `orgMcp`/`orgMcpFetch` (asked each turn; never in child mode; a deployment server's id wins) and the capabilities route's `mcp` list.
- Box connectors (CNX-4): `where: box` (base may be http and an office address; operations may have `format: xml`, the body text with the input `xmlEscape`d); `callConnector` refuses them (409), so the server and routines never call them; `boxConnectorJson` is what the box installs. The box (`apps/box/src/connectors.js`, zero-dependency: `checkConnector`, `buildRequest`, `callBoxConnector`; tables `connectors` and `connector_secrets`, migration 7) calls only installed ones at `POST /v1/connectors/:id/:op` (`GET /v1/connectors` lists them, secrets by name); `yaxb-box connector add|list|remove|secret` (main.js; the secret from stdin). Web: `KioskShell.connectorCall` sends a box connector's step (and a guard's `call`) to the connected box; the workspace's "On the box" view (`catalogue/BoxConnectorSetup.vue`) downloads the file and shows the commands.
- CNX-8: every call (the connector route and routines) is a `connector.called` event on the connector's entry (`connectorCalled` in kiosk.ts): the operation as journey, ms and ok, never the payload.

## The Scheduler (SCH-1..8)

- **Core** `schedule/` (export `./schedule`): `scheduleItemSchema` (kinds todo, birthday, anniversary, event; `repeat` none/weekly/monthly/yearly; `person`; `owner`), `occurrences(items, from, to, services)` (yearly from 29 February falls on 28 February; `years`), `upcoming(items, today, days, services)` → `{ dated, overdue, undated }`, `parseScheduleText(text, today)` (on-device reading of dates, weekdays, "tomorrow", "next Friday", times), and `SCHEDULE_FORM`/`scheduleFields()`/`draftFromFills` for the model pass: `kiosk.extract()` takes the Scheduler's form and tells the model today's date.
- **Service dates**: nested services may carry `dates: [{ id, title, date: YYYY-MM-DD, time?: HH:MM }]` (yaxb-journeys `serviceDates`, checked in `expandService`); `ServiceDesign.dates` and the "Key dates" fieldset on ServiceDesigner's Service step.
- **Web**: `composables/schedule.ts` (`useSchedule`: IndexedDB `yaxb-schedule`, per profile owner; services' dates from loaded catalogue services; `draft()` reads on the device, then the model; `pendingScheduleText`), `SchedulerScreen.vue` inside Quick tools (`/kiosk?screen=services&tool=scheduler`; the `scheduler` screen in `screens.yaml` is hidden, and its Quick tools item opens the tool), `ComingUp.vue` in Ask Me's empty state. In the composer, `/schedule <words>` and `/qt` (the `ContextSheet` mode `qt`, picks of kind `tool`, `KioskShell.openTool`); neither at the front desk.

## Attendance (ATT-1..4, 6)

- Core `attendance/` (export `./attendance`): `Roster` (departments, shifts with `grace` and `days`, employees with `pin_hash` from `hashPin(id, pin)` and a card `qr`, sites with `radius_m`), `rosterProblems`, `whoChecks`, `checkOutcome` (`attendance.in|late|out`, India time by default), `insideSite`, `rosterReport(roster, events, from, to)`, `reportCsv`, `rosterCsv` (`toCsv` guards formulas). Seed `content/catalogue/attendance.service.yaml` (journey `check-in`, handler `attendance.check`, `where: "device"`). There is no import (ATT-5 dropped).
- Web: `composables/attendance.ts` (localStorage `yaxb.attendance.roster`, synced as service data `attendance-roster`; `library.ts` `applyServiceData` applies it, newer `updated_at` wins); KioskShell's `attendance.check` records a `journey.outcome` event with the employee as `actor` (and only `site:<id>` or `outside` when sites are set); `moderation/AttendanceStaff.vue` is For staff → Attendance (Report and Roster).
